# SYS_SPEC —— dsh_Windows_MCP 系统规格

> **本文件的作用**：它是本项目的**规格真源**（SDD）。任何实现、测试、文档与它的
> 表述冲突时，以本文件为准；如果本文件本身不合意，先改本文件再改代码。
>
> **为什么需要它**：本项目的核心价值不在"能调用工具"，而在**行为承诺**——
> 什么情况下必须拒绝一次点击、坐标怎么换算、审计记什么。这类承诺如果只存在于
> 代码里，就无法被独立复核，也无法在重构时保住。规格必须是可以被人读、
> 被测试逐条覆盖（见 `../features/` 与 `COVERAGE.md`）、被对抗性验证者挑战的东西。
>
> **书写约定**：
> - 每条规格有稳定编号 `S-<域>-<序号>`，永不复用、永不重排。
> - 每条规格必须可判定（能写出一个会因它失败而失败的测试），否则不写进来。
> - 标记 `[UNVERIFIED]` 的条目表示「已按此实现但尚未在真机/真实边界上验证过」，
>   必须连同未验证的原因一起写出。没有这个标记的条目表示**已实测**。
> - 域白名单由 `test/spec/coverage.js` 的 `SPEC_DOMAINS` 持有；编号不落在白名单里的
>   条目不会被覆盖门统计（占位符 `S-<域>-<序号>` 天生不匹配）。新增域必须同步加白名单。

## 0. 术语

| 术语 | 定义 |
|---|---|
| **观测（observation）** | 对 `mcp__<server>__Snapshot` / `Screenshot` 结果的结构化解析产物：光标位置、截图区域、缩放系数、上游图片尺寸、附件尺寸、焦点窗口、可交互元素、时间戳、id、代次 |
| **观测 id** | 形如 `obs-<n>` 的字符串，`n` 在**进程内全局单调递增**，跨会话不重复 |
| **代次（generation）** | 每个 agent 会话桶内单调递增的计数，用于判断「是否有更新的观测」 |
| **输入类动作** | Click / Type / Scroll / Move / Shortcut / MultiSelect / MultiEdit |
| **只读观测工具** | Snapshot / Screenshot / DisplayInventory / Wait / WaitFor |
| **高影响工具** | App / PowerShell / FileSystem / Registry / Process / Clipboard / Notification |
| **映射（mapping）** | 由观测推导出的「图片像素 ⇄ 屏幕坐标」仿射关系 |
| **闸门（gate）** | 动作执行前的判定，可放行或拒绝 |
| **失败关闭（fail closed）** | 任何内部异常/信息缺失一律按「拒绝」处理，绝不默认放行 |

## 1. 坐标映射

### S-MAP-01 映射公式
对一次观测，图片像素 `(px, py)` 到屏幕坐标的换算是**纯乘法加原点平移**：

```
screen_x = origin_x + px * screenPerImagePx
screen_y = origin_y + py * screenPerImagePx
```

`origin` 取 `Screenshot Region` 的左上角；缺该行时取 `(0, 0)`。

### S-MAP-02 缩放系数只来自 coord_scale
`screenPerImagePx = coord_scale`，其中 `coord_scale` 是结果里
`Screenshot Coordinate Scale:` 的数值；缺该行时取 `1.0`。

**"缺行"与"值非法"必须区分**（对抗性验证引入）：行存在但值不是正有限数
（`0` / 负数 / 非数字）时，换算退化为 `1.0`，但**诊断必须说明是值非法**，
不得谎称"缺少该行"——错误的诊断会把排障方向带偏。

**明确禁止**再乘「附件宽 / 上游图片宽」。该做法曾被实现并在真机上被证伪：
本机 `coord_scale = 1.333333`、上游图 `2560x1440`、落盘附件 `1920x1080`，
而 `1920 = 2560 / 1.333333` —— `coord_scale` 本身已是完整因子。叠加附件比例会
把「关闭」按钮预测到图片 `x≈1417.5`，实测在 `x≈1890`。

（`previewWidth` 参数是唯一的例外逃生口，仅在显式传入且与上游尺寸不同时生效，
且该分支标记 `[UNVERIFIED]`。）

### S-MAP-03 无偏移 `[真机测量项]`
实测两点拟合：`slope = 1.333333`、`intercept = 0.0000`。125% DPI **不需要**补偿。

这是**真机测量断言**（裁决 A-14），进程内无法判定。真机复核时的容差：
`|intercept| < 0.01`、`|slope - coord_scale| < 1e-6`。

### S-MAP-04 实测锚点（回归基准）
在本机 `2560x1440`、缩放 125%、单显示器配置下，以下对应关系必须成立：

| 屏幕坐标 | 图片像素 | 来源 |
|---|---|---|
| (2520, 35) | (1890, 26.25) | 「关闭」按钮；用 `use_annotation=true` 的 CURSOR 红十字无残差探针验证 |
| (2000, 720) | (1500, 540) | 光标位置探针 |

另有一条**可断言**的原点关系（裁决 A-15，替代原先那句非断言描述）：
`imageToScreen(0, 0, mapping)` 必须等于 `(region.left, region.top)`。

### S-MAP-05 映射不可用时必须显式失败
缺少 `Screenshot Coordinate Scale` **且**缺少 `Screenshot Original Size` 时，
映射标记为不可用，换算接口必须抛出可读错误；**不得**静默返回输入值或猜测。

### S-MAP-06 数值友好化与误差界
换算结果与最近的整数相差不超过 `0.002` 时吸附到该整数——但**仅当
`screenPerImagePx >= 1`**。

理由：`coord_scale` 是上游四舍五入过的值，`1890 × 1.333333 = 2519.99937`，
输出 `loc=[2519.999, …]` 会诱发模型反复微调。但在 `coord_scale << 1` 时，
吸附误差会被放大（实测 `coord_scale = 0.0001` 时往返误差达 **19.9 图像像素**），
因此那里必须关掉吸附。

**误差界**（可判定）：往返换算的图片像素误差须满足
`|Δpx| <= 0.002 / screenPerImagePx`。裁决 A-04。

### S-MAP-07 映射摘要必须单行
给模型看的映射摘要必须是**一行**、且是 `key=value` 形式，避免污染上下文。

### S-MAP-08 附件说明里的预览尺寸必须被解析并核对
DSh 的图片块会带一段附件说明，形如：

```
Image sha256:<64 hex>; request preview 1708x961px. Normalized copy (read-only; may be resized
or re-encoded): "<...>" (1920x1080px, image/png). Source dimensions, format, and byte size may differ.
```

其中有两个不同的尺寸，语义完全不同：

| 片段 | 含义 |
|---|---|
| `request preview WxHpx` | DSH **请求**渲染的预览尺寸（预算相关，**不**代表模型看到的就是这个尺寸） |
| `Normalized copy … (WxHpx, image/png)` | DSH 实际交给模型的**归一化副本**尺寸 |

必须解析**两者**，并在它们**不相等**时给出诊断。

理由：卡内基（坐标换算）假设"模型看到的图 = 归一化副本"。如果 DSH 真的把预览缩放后
才交给模型，那么这个假设就不成立，而换算会**静默偏掉**。把这两个数字显式解析出来并核对，
就把"提醒里有没有出现需要人工介入的情形"变成了**可判定**的事——
这比继续把 `previewWidth` 当作纯假设要强。

该诊断**不改变换算**（不猜、不自动补偿）：只把事实摆出来。
自动补偿需要先知道"模型到底看到了哪一张图"，那属于 U-02 未验证的部分。

## 2. 动作闸门

### S-GATE-01 失败关闭
闸门内部任何异常（策略评估抛错、数据形状异常）都必须导致**拒绝**，
并以机器可读的 `code` 说明原因。绝不默认放行。

### S-GATE-02 无观测
输入类动作在没有可用观测时被拒绝，`code = NO_OBSERVATION`，
原因文本必须包含「先 Snapshot」这一可执行动作。

### S-GATE-03 过期
观测年龄**大于** `maxObservationAgeMs` 时拒绝，`code = STALE_OBSERVATION`。
年龄**恰好等于**上限时**不**算过期（边界）。

### S-GATE-04 代次落后
若在依据的观测之后又产生了更新的观测，即使年龄很小也拒绝，
`code = STALE_OBSERVATION`。

### S-GATE-05 窗口漂移
依据的观测所记录的焦点窗口，与执行时的焦点窗口在
`pid / executable / title / handle` 任一字段上不同时拒绝，`code = PROCESS_CHANGED`。
任一侧缺失进程信息时**跳过**该判定（避免把「没数据」当成「变了」）。

### S-GATE-06 引用的观测必须存在
输入类动作若在参数里声明了 `based_on`（亦接受 `basedOn` / `observation_id`），
则该 id 必须在本会话的观测历史中真实存在；否则拒绝，`code = UNKNOWN_OBSERVATION`，
且原因文本必须同时给出「你写的 id」与「当前可用的最新 id」。

**三态契约**（对抗性验证引入）：该字段的取值只有三种合法解释——

| 情况 | 处理 |
|---|---|
| 字段不存在，或显式为 `null` | 视为"未声明依据"，不做该校验 |
| 字符串且去空白后非空 | 合法 id，必须存在 |
| 字段存在但类型非法（数字/数组/对象/布尔/空串） | **拒绝**（`UNKNOWN_OBSERVATION`） |

第三种**不得**当成"未声明"。把它静默忽略会让 `based_on: 99` 这类输入通过，
而模型以为自己声明了依据——这正是该校验要防的幻觉。

### S-GATE-07 只读工具不因闸门原因被拦
`Snapshot / Screenshot / DisplayInventory / Wait / WaitFor` **不因以下原因**被拦：
观测缺失、观测过期、代次落后、映射不完整、急停启用。

**操作者显式配置的策略判定不在此列**——例如 `denyTools` 明确拒绝某个只读工具时，
它照常被拒。原措辞"任何情况下"与"策略可拒绝任何工具"冲突，已在裁决 A-09 收窄。
否则系统无法自救。

### S-GATE-08 非本插件的工具不受影响
`serverName` 之外的 `mcp__*` 工具，以及所有非 MCP 工具，闸门不介入。

### S-GATE-09 映射不完整不阻断
观测缺少坐标映射信息时只产生提示，**不**构成拒绝（UI 树坐标仍然可用）。

### S-GATE-11 配置开关的边界（裁决 A-10）
显式承认三个逃生口，且**仅限这三个**：

| 开关设为 `false` | 关闭的判定 |
|---|---|
| `requireObservation` | S-GATE-02（无观测拒绝） |
| `requireCoordinateMapping` | S-GATE-09 的提示 |
| `requireProcessMatch` | S-GATE-05（窗口漂移） |

除这三个显式开关外，**任何配置都不得使 S-GATE-\* 失效**（与 S-CFG-02 一致）。
不得存在"某个未文档化的配置项让闸门形同虚设"的路径。

### S-GATE-10 依据的观测必须属于本会话
`based_on` 指向的 id 若属于其他 agent 的观测桶，视为不存在。

## 2b. 失败关闭（决策形状契约）

> 本节由**对抗性验证**引入：验证者构造出「策略返回 `{}`」这一反例，使整个
> 新鲜度检查被跳过——没有观测也能点击。失败开放（fail-open）是安全组件最不可
> 接受的缺陷类型，因此把"只接受明确定义的决策"提升为独立规格。

### S-FAIL-01 只接受明确定义的决策
闸门对策略返回值的接受集合**恰好**是：

- `{ kind: 'allow' }`
- `{ kind: 'deny', reason: <非空字符串> }`
- `{ kind: 'ask' }`

其它任何形状——`{}`、`null`、`undefined`、字符串、数字、数组、未知 `kind`、
`deny` 但缺 `reason`——一律视为策略失败，按拒绝处理并给出 `code = POLICY_ERROR`。
**不得**存在"既不是 allow 也不是 deny/ask 于是放行"的路径。

### S-FAIL-02 异常与畸形输入不得让闸门崩溃
策略抛出任何值（Error / 字符串 / null）、策略对象缺少或不是函数的 `evaluate`、
配置对象带有抛异常的属性 getter，都必须导致**拒绝**或**退化为默认值**，
而**不得**把异常抛给调用方，也不得让插件挂载失败（与 S-HOST-04 一致）。

### S-FAIL-03 放行必经完整新鲜度检查
`allow` 只是"策略层面同意"，不构成放行。新鲜度（S-GATE-02…06、S-GATE-10）
必须无条件叠加且其结论优先。任何"策略 allow 就跳过新鲜度"的实现都是缺陷。

## 3. 观测存储

### S-OBS-01 id 全局唯一
观测 id 的序号在进程内全局单调递增，**不**随 agent 重置。理由：id 会进入审计日志
与被模型引用的 `based_on`，若不同会话各自从 `obs-1` 开始，日志无法复盘。

### S-OBS-02 代次按 agent 单调
`generation` 是「每个 agent 会话桶内」的单调递增计数，从 1 开始。

### S-OBS-03 会话隔离
一个 agent 的观测（当前值、历史、按 id 查询）不得被另一个 agent 读到。
多 agent 并发调用时必须各归各的桶。

### S-OBS-04 有界历史
每个会话桶最多保留最近 20 条观测。

`history(agent, limit)` 的 `limit` 必须是**上限**语义：`limit <= 0` 或非有限数时
返回**空数组**，而不是"全部"。返回比请求更多的条目会让调用方的分页/截断逻辑失效
（对抗性验证指出 `limit=0` 曾返回全部 20 条）。

### S-OBS-05 解析必须容错
解析真实输出时必须容忍：CRLF 行尾与残留 `\r`、中文控件名、包含空格与 em dash
的窗口标题、负数坐标、缺失的区块。任何单块解析失败都不得让整条观测失败。

### S-OBS-06 属性按行界定
UI 元素的 `[action:]` / `[focused]` / `[value:]` 属性只在该元素**所在行**内匹配。
禁止使用固定长度字符窗口向后看——该缺陷曾导致后面元素的 `[focused]`
被挂到前面元素上，使「哪个元素有焦点」全错。

## 4. 安全开关

### S-SAFE-01 急停语义
急停启用后，除只读观测工具外的所有本插件辖内工具调用被拒绝。

`engage` 是**幂等**的，语义为「保持第一次启用的现场」：

- 重复 `engage` **不**增加启用计数；
- **不**刷新启用时间；
- **不**覆盖第一次记录的原因（第一次的原因才是"用户为什么喊停"的答案）；
- 但 `engageCount` 会记录累计尝试次数，便于诊断"谁在反复尝试停手"。

`release` 后恢复放行；再次 `engage` 视为新的一次启用（计数 +1，时间与原因刷新）。

### S-SAFE-02 急停的同步兜底
急停必须同时通过同步守卫生效，保证即使前置闸门链路异常，输入类动作仍被拦住。

### S-SAFE-03 审批不可用时失败关闭
当策略要求审批（`requireApproval` / `requireApprovalForInput`）但审批通道不可用时，
必须拒绝并给出 `APPROVAL_UNAVAILABLE`，不得放行。

### S-SAFE-04 审批授权一次性且会过期
审批授权在通过的那一次调用后被消耗。

过期边界（裁决 A-11）：授权在 `now - grantedAt > approvalTtlMs` 时失效；
**恰好等于上限时仍然有效**（与 S-GATE-03 的边界约定一致）。
`approvalTtlMs <= 0` 表示立即失效。

## 5. 审计

### S-AUDIT-01 只追加
审计是 append-only JSONL；不得就地修改或删除既有行。

### S-AUDIT-02 审计失败绝不影响动作
审计写入失败必须被捕获并计数，**不得**改变动作结果，不得向调用方抛错。

### S-AUDIT-03 时间戳形状统一
所有条目的 `at` 一律为 ISO 8601 字符串。接受毫秒数 / Date / 可解析字符串作为输入。
理由：曾出现策略层写毫秒数、插件主体写 ISO 的混合形状，使按时间读日志不可靠。

**不可解析的 `at`**（裁决 A-08）：用**写入时刻**的 ISO 字符串兜底，并在条目上标
`atCoerced: true`。不得原样保留原字符串——那会让"按时间排序"失效，且看不出被替换过。

**"未提供"与"不可解析"必须区分**（裁决 N8）：

| 输入 | 处理 | `atCoerced` |
|---|---|---|
| `at` 缺失或 `null` | 用写入时刻（"未提供"，不是被替换） | **不标** |
| `at` 存在但非法（垃圾串 / `NaN` / `Infinity` / **有限但超出 `Date` 范围**） | 用写入时刻兜底 | 标 `true` |

**字符串 `at` 的方言语义**（裁决 N9）：纯数字串（`/^-?\d+$/`）按**毫秒时间戳**解析；
其余走 `Date.parse`。不得依赖 `Date.parse` 对短数字串的方言行为——
`Date.parse('0')` 会被解释成 2000-01-01，而我们要的是纪元 0。

实现**不得**因越界数值抛异常：那会让 `record()` 吞掉条目并计一次 `writeFailures`，
使审计条目彻底丢失，与 S-AUDIT-07 冲突。

### S-AUDIT-04 脱敏
写入前必须脱敏：

- **密钥样式键名**：键名中出现 `key` / `token` / `secret` / `password` / `passwd` /
  `pwd` / `credential` / `cookie` / `session` / `jwt` / `bearer` / `signature` /
  `sig` / `auth` / `authentication` / `authorization` / `apikey` 等词（大小写不敏感，
  且需覆盖 `accessKey` 这类 camelCase 与 `session_id` 这类下划线形式）时，其值整体打码。
- **超长编码串**：任意位置出现超过 200 字符的连续 base64/hex 串时打码。
- **图像类字段**：`image` / `screenshot` / `dataurl` / `base64` / `blob` 等键的
  字符串超过 64 字符时整体打码。图片 base64 绝不落盘。

**误打码的方向性选择**：本规格允许（并要求）宁可多打码——
`monkey` 这类含 `key` 的普通键名会被误打码。理由是审计里多几个 `<redacted>`
只是难读，而少打一个就是凭据明文落盘。因此脱敏判定**不锚定词首边界**。

### S-AUDIT-05 撕裂行容错
读取时最后一行若被截断，跳过该行而不是抛错；文件不可读时回退到内存环形缓冲。

**记录形状**（裁决 A-05）：`read()` **只返回 JSON 对象**。`5` / `"x"` / `null` / `[]` /
`true` 这类"合法 JSON 但不是记录"的行按损坏行处理，跳过并计入 `stats().skipped`。
理由：消费方读 `entries[i].observationId` 会直接抛错；而且"静默丢弃"与
"统计到丢了多少行"在排障时完全不同。

### S-AUDIT-06 有界
文件超过 `auditMaxBytes` 时轮转，最多保留 `rotateKeep` 份历史。

### S-AUDIT-07 记录放行与拒绝
放行、拒绝、观测、工具报错都必须留下条目；拒绝条目必须带 `code` 与 `reason`。

## 6. 宿主集成

### S-HOST-01 挂载点
插件通过 `tools/pre-execute`（前置闸门）、`tools/post-execute`（观测与富化）、

坐标映射与提示以**追加内容块**的形式附加在原始结果之后，绝不替换上游内容。
即使映射算错，模型仍能看到 Windows-MCP 原文。

**上游内容源的定义**（裁决 A-12）：依次取 `result.content`（数组）→
`result.value.content`（数组）→ `result.value`（字符串）。
富化结果**必须以上游内容开头**，追加块只能位于其后；上游为空时追加块本身即结果。

### S-HOST-03 生命周期
`apply` 必须返回可释放的清理函数，并注册进 `ctx.effect`；卸载后不得留下
监听器、守卫或已注册工具。

### S-HOST-04 不阻断插件树
本插件自身的任何失败都不得让整棵插件树启动失败。启动日志必须给出可执行的修复信息。

**"可执行的修复信息"的度量**（裁决 A-07）：任何配置字段被强转或回退默认时，
必须 `warn` 一条含**键名 / 收到值 / 采用值**的日志。静默把
`maxObservationAgeMs: 'x'` 变成 `60000` 是"看起来生效其实没生效"的典型缺陷，
用户永远查不到原因。

### S-HOST-05 桥接行的所有权
本 bundle **不**插入 `mcp-winmcp` 桥接行（由 profile 持有），只插入自己的行
`dsh-windows-mcp`。任何 id 有且只能被一个层 insert。

## 10. 持久上下文注入（Batch 2）

### S-CTX-01 观测状态进入运行时上下文
每次模型步骤组装提示词时，必须把**当前会话最新观测**的以下几项作为运行时上下文注入：

- 观测编号（供 `based_on` 引用）
- 该观测对应的坐标换算系数与原点
- 观测年龄
- 焦点窗口名（若已知）

理由：坐标换算系数只挂在一次工具结果之后时，模型在后续步骤里只能靠记忆复用；
而它一旦记错，就是一次点偏。放进每轮都重建的上下文，才不会随对话增长而丢失。

### S-CTX-02 会话隔离
上下文必须是**每个 agent 会话各自**的：A 会话的观测不得出现在 B 会话的提示词里
（与 S-OBS-03 一致）。跨会话串用等于把"我依据哪次观测"这件事整体作废。

### S-CTX-03 无观测时不注入
本会话没有任何观测时，该上下文贡献**不产生任何文本**（`undefined` 或空串），
不得写出"无观测"这类占位文本——那会白占 token 且毫无信息量。

### S-CTX-04 单行且有界
注入文本必须是**一行**，且长度有上限（超限截断）。上下文在每一轮都出现，
多行或超长会持续挤占上下文预算。

**"一行"的判定方式**（裁决 N3）：文本中**不得出现** `\r`、`\n`、`\u2028`、`\u2029`
（以及其余 C0 控制字符）；任何来源（含焦点窗口名）的这类字符一律折叠为单个空格。
可判定断言：`text.split(/\r\n|\r|\n|\u2028|\u2029/).length === 1`。

### S-CTX-05 注入失败不得影响对话
系统提示服务缺失、注册抛错、或在组装时取值抛错，都必须退化为"不注入"，
**不得**让模型调用失败或让插件树启动失败（与 S-HOST-04 一致）。

### S-CTX-06 可关闭
配置 `injectContext: false` 时完全不注册该上下文贡献。

## 11. 命令级策略（Batch 3）

> **目标**：`PowerShell` / `Registry` / `FileSystem` / `Process` 目前只做分类与审计，
> **不解析内容**。于是 `Remove-Item -Recurse -Force C:\` 与 `Get-Date` 在策略眼里一模一样。
> 本节引入"按内容判定"的最小机制。

### 设计立场：**只做能确定性判定的部分**

命令级策略最危险的失败方式是**假阳性**（把正常开发操作拦死，用户于是整体关掉它）
与**假阴性被当成保证**（以为拦住了，其实换个写法就绕过）。

因此本节的规则刻意保守：
- 只匹配**明确的危险模式**，不试图理解任意 PowerShell 语义；
- 采用**子串匹配**（不是完整的 shell 解析）——绕过是可能的，规格**明确写出这一点**，
  不把它包装成"安全边界"；
- 判定不了时**失败关闭**，但"判定不了"只指解析过程出错，不指"没匹配上任何规则"。

### S-CMD-01 操作文本的来源
命令级判定使用的"操作文本"按工具类目从参数拼装（顺序固定，便于规则撰写）：

| 类目 | 取值字段 | 拼装格式 |
|---|---|---|
| `PowerShell` | `command`（字符串）或 `script` | 原值 |
| `Registry` | `action`、`path`、`name`、`value` | `<action> <path> <name> <value>`（缺失字段跳过） |
| `FileSystem` | `operation`/`action`、`path`/`paths` | `<op> <path...>` |
| `Process` | `action`、`name`/`pid` | `<action> <name> <pid>` |
| 其它 | — | 不产生操作文本 |

拼装后做**规范化**（S-CMD-02）。若类目需要文本但一个字段都取不到 → 见 S-CMD-06。

### S-CMD-02 规范化必须确定
规范化恰好做三件事，且顺序固定：

1. 转小写；
2. 把所有连续空白（含制表符/换行）折叠成一个空格，并去首尾空白；
3. 把 `\` 与 `/` 统一为 `/`。

理由：路径分隔符与大小写是同一操作最常见的两种写法差异。规范化让
"写规则的人"和"看审计的人"看到同一个字符串。**不做**引号去除、变量展开、
转义还原——那需要真正的解析器，超出本节的立场。

### S-CMD-03 规则格式：规范化子串
`commandRules` 是 `{ id, pattern, risk, reason }` 数组。
`pattern` 是**规范化子串**（不是正则）：命中条件为
`normalizedOperation.includes(normalizedPattern)`。

选择子串而非正则的理由：正则里 `\` 与 `.` 的转义是配置错误的高发区，
而本节的规则是"关键词黑名单"性质，子串足够且不可能写坏。

### S-CMD-04 内置危险规则必须始终生效
以下**内置**规则（`pattern` 为规范化子串）默认全部启用，且不得被配置**移除**——
只能通过显式的 `allowRules` 豁免（S-CMD-07）：

| id | 命中子串（已规范化） | 风险 |
|---|---|---|
| `recursive-delete` | `remove-item -recurse` | 递归删除 |
| `recursive-delete-alias` | `rm -r` | 递归删除（PowerShell 别名） |
| `recursive-delete-cmd` | `rd /s` | 递归删除（cmd 写法） |
| `recursive-delete-del` | `del /s` | 递归删除（cmd 写法） |
| `filesystem-wipe-drive-root` | *(复合)* `delete` ∧ `recursive` ∧ 驱动器根 | FileSystem 清空整个分区 |
| `process-force-kill` | *(复合)* `kill` ∧ `force` | Process 无条件强杀进程 |
| `app-launch-interpreter` | *(复合)* `launch`/`launch_executable` ∧ 解释器名 | 通过 App 启动解释器（绕过命令级策略的执行路径） |
| `format-volume` | `format-volume` | 格式化卷 |
| `format-disk` | `format c:` | 格式化磁盘 |
| `clear-disk` | `clear-disk` | 清盘 |
| `registry-delete-hklm` | `remove-item hklm:` | 删 HKLM 注册表键 |
| `registry-delete-hkcr` | `remove-item hkcr:` | 删 HKCR（文件关联/COM 注册） |
| `registry-remove-hklm` | `remove-item -path hklm:` | 删 HKLM 注册表键（`-Path` 写法） |
| `registry-hive-destructive-hklm` | *(复合)* 首位删除动作 ∧ `hklm:`/`hkey_local_machine` | Registry 类目下删 HKLM |
| `registry-hive-destructive-hkcr` | *(复合)* 首位删除动作 ∧ `hkcr:`/`hkey_classes_root` | Registry 类目下删 HKCR |
| `force-kill-process` | `stop-process -force` | 强杀进程 |
| `shutdown-machine` | `stop-computer` | 关机 |
| `restart-machine` | `restart-computer` | 重启 |
| `disable-execution-policy` | `set-executionpolicy unrestricted` | 放开脚本执行策略 |
| `disable-firewall` | `set-netfirewallprofile -enabled false` | 关防火墙 |
| `disable-defender-realtime` | `set-mppreference -disablerealtimemonitoring` | 关实时防护 |

> **这张表与代码必须逐字一致，由测试双向强制**（`S-CMD-11`）。
> 曾经撞到过：表里写了 5 个代码里不存在的规则 id，同时漏掉 7 个真实存在的规则——
> 于是"规格说会拦"和"实际会拦"是两套东西。
> 这正是 `S-CFG-01` 在配置面防的那类漂移，在规则面上同样致命。
>
> **复合规则**（表格里标 *(复合)*）用于子串表达不了的判断，例如
> `hklm:` 单独出现太宽——会把**只读查询**也拦掉，而假阳性会让人整体关掉这个功能。
> 因此 `registry-hive-destructive-*` 要求"配置单元 ∧ 删除动作"同时成立。
> 这是对抗性验证 V2 的直接产物：修之前，Registry 类目下删除 HKLM **永远不命中**，
> 因为那三条 registry 规则的 pattern 都以 `remove-item` 开头，而 Registry 的
> 操作文本里 `action` 是注册表动作名（`delete`/`remove`/…），不可能是 PowerShell cmdlet。

### S-CMD-11 规则表与代码必须一致
`DEFAULT_COMMAND_RULES` 的**每一条**（id 与 pattern 逐字）都必须出现在本节的表里；
本节的表里**不得**出现代码里没有的 id。由测试双向强制。

理由：表里多写一条会让读者以为某个危险操作被拦住了（其实没有）；
少写一条会让读者以为某个操作安全（其实被拦）。两者都是**关于安全的错误陈述**。

> 这些是**关键词黑名单**，绕过方式很多（拼接、变量、编码、别名）。
> 规格明确声明：它们**不是**安全边界，只是把最常见的一批危险写法从"静默放行"变成"明确拒绝"。

### S-CMD-05 拒绝理由必须可执行
每条规则的 `reason` 必须说明**为什么危险**，拒绝文本还必须给出
"如果你确实需要，请让用户显式配置 `allowRules`"这一出路。
只给代码不给理由会让模型反复重试同一个命令。

### S-CMD-06 取不到操作文本时不得静默放行
「不可评估」的判定必须区分三种情况：

| 输入 | 处理 |
|---|---|
| 调用方**未提供参数**（`args` 为 `undefined`） | 这次判定**没有内容依据**，跳过命令级判定（交给后续规则） |
| 提供了参数，但拼装出的操作文本**规范化后为空** | **拒绝**，`code = CMD_UNEVALUABLE` |
| `null` 或不支持的类型（数字/布尔/函数） | 与上一行同等处理（**拒绝**） |

**判据是"规范化后是否为空"，不是"有没有那个键"**（裁决 N1）。
`{command:''}` / `{command:'   '}` 拼装出来是空串，所有规则都不命中，
于是会**静默放行**——而"命令文本为空"恰恰是判定不了。
取到但值为 `0` 属"取到了"（`String(0) = '0'` 非空），走规则匹配。

**为什么必须区分**：命令级策略只在**有内容可判**时才有资格发言。把"根本没传参数"
也判成不可评估，会让所有不关心内容的调用方无辜被拒（实测：一次性打挂了 6 个既有测试，
它们只是在验证别的规则）。而调用方声称"这就是该工具的参数"却给不出命令文本时，沉默就是漏洞。

判定不了 ≠ 没命中规则。前者必须拒绝；后者按 S-CMD-08 放行。

### S-CMD-07 豁免只在显式配置时生效
`allowRules` 是规则 id 数组。命中内置规则但其 id 在 `allowRules` 中时**不拒绝**，
但必须在审计里留下 `ruleExempted: <id>`，让"谁在什么情况下用了豁免"可复盘。

### S-CMD-08 未命中任何规则时放行
命令级策略只在**命中**时改变决定。未命中一律交给后续判定（审批/新鲜度），
**不得**因为"没看懂"而拒绝——否则每条正常命令都要人肉批准。

### S-CMD-09 命令级拒绝优先于审批
命中危险规则的调用直接 `deny`，**不进入**审批流程。
理由：审批是"允许人决定"，而这类操作是"默认不该做"；
让人批准一次 `Remove-Item -Recurse C:\` 本身就是设计缺陷。

### S-CMD-10 可关闭
配置 `commandRulesEnabled: false` 时完全跳过命令级判定（退回 Batch 2 的行为）。

**该开关必须在两层一致生效**（裁决 N2）：策略层（`lib/policy.js`）与纯函数层
（`lib/commands.js::evaluateCommand`）都必须尊重它。曾经策略层正确跳过、
而直接调用纯函数仍然拒绝——同一个开关两套行为不可接受。

### S-CMD-12 拼装字段名必须来自上游真实 schema
命令级判定的**字段名**必须与上游工具的真实参数名一致，且由测试反向校验：
每个拼装用到的键都必须存在于 `WINDOWS_MCP_ARGUMENTS`，每个类目都必须读取真实的动作字段。

为什么单独设一条：曾经凭猜测写了 `action`/`operation`/`paths`/`script`，
而真实工具用的是 **`mode`**（实机 introspection 见 `_recon_tools/REPORT-mcp-contract.md`）。
后果是规则表在每一份文档里看起来都对，**真机上却永远命中不了**——
而单元测试用了同样猜错的键，所以全绿。这是"测的是空气"的典型案例，
也是真机验证（Batch 6）唯一的实质产出。

布尔修饰符同理：`recursive` 是"删一个文件"与"删整棵树"的唯一区别，
必须在其为真值时进入操作文本（假值不进入，避免误命中）。

**真值方言：必须逐字照抄上游，不得"合理推断"**（对抗性验证 V2）。

上游 `tools/filesystem.py:47` 与 `tools/process.py:37` 用的是同一写法：

```python
recursive = recursive is True or (isinstance(recursive, str) and recursive.lower() == 'true')
```

因此真值判断**恰好**是：布尔 `True`，或字符串 `lower()` 后等于 `'true'`。
由此推出几条反直觉但必须遵守的结论：

| 输入 | 上游真值 | 说明 |
|---|---|---|
| `true` / `'true'` / `'True'` / `'TRUE'` | **真** | `lower()` 后相等 |
| `' true '`（带空白） | **假** | 上游**不 trim** |
| `'1'` / `'yes'` / `1` / 非零数 | **假** | 既不是 `is True`，也不是 `'true'` |

> **这里曾经写错过**：本文档一度要求"必须覆盖 `'1'`、`'yes'`、非零有限数"，
> 实现照做，于是 `recursive:'yes'` 被拒——而上游根本不会递归删除。
> 那是**假阳性**，正是本模块自己声明最怕的缺陷。
> 教训：**安全方向不等于"宁可多认"**。方向只能是照抄上游：
> 上游不递归，就没有东西要拦。凡是"上游语义"，必须读源码，不能推断。

### S-CMD-15 卷根与配置单元的等价写法必须穷尽（V1 失败开放）
`S-CMD-13` 只覆盖了注册表配置单元的别名，**卷根漏了同类问题**，导致失败开放：

| 写法 | 规范化后 | 修复前 |
|---|---|---|
| `C:\` / `C:` / `C:/` | `c:/` | 拦 ✅ |
| `\\?\C:\` | `/?/c:/` | **放行 ❌** |
| `\\.\C:\` | `/./c:/` | **放行 ❌** |

`\\?\` 与 `\\.\` 是 Windows 命名空间前缀，表示**同一个路径**、只是要求不做路径规范化；
上游 `Path('\\\\?\\C:\\').is_dir()` 为真，会走 `shutil.rmtree`——**真的清空分区**。

因此规范化必须**去掉这两个前缀**（在词首或空格之后），使等价写法归一到同一形态。
这条已并入 `S-CMD-02` 的规范化步骤 4。

### S-CMD-13 注册表配置单元别名必须覆盖
`HKLM:` / `HKCR:` 是 PowerShell 的**简写**，等价的合法写法还有
`HKEY_LOCAL_MACHINE:\...`、`HKEY_CLASSES_ROOT\...`、`Registry::HKEY_LOCAL_MACHINE\...`。
规则必须覆盖这些别名，否则留下绕过路径。

**动作词必须锚定在操作文本首位**（`^`）：操作文本是
`<mode> <path> <name> <value>`，若动作词允许出现在任意位置，
`Registry mode=get path=HKLM:\... name=Remove`（读取一个**值名为 Remove** 的值）
会被误判成破坏操作——这是对抗性复核发现的假阳性，而假阳性会让人整体关掉这个功能。

### S-CMD-14 `Process` 命令级覆盖范围（事实前提已更正）
上游 `tools/process.py` 的真实签名是：

```python
def process_tool(mode, name=None, pid=None, sort_by="memory", limit=20, force=False, ...)
```

其中 **`force` 决定 `p.kill()`（无条件强杀）还是 `p.terminate()`**，是**可区分字段**。

因此本节的结论分两半（对抗性验证 V3 指出原文把"`Process` 只有 `name`/`pid`"写错了）：

1. **`mode=kill` 且 `force` 为真** → **拦截**（规则 `process-force-kill`）。
   这是无条件强杀，与 PowerShell 的 `Stop-Process -Force` 同类。
2. **`mode=kill` 但不带 `force`**（即 `terminate`）→ **不在命令级拦截**，
   交由审批层（`requireApproval`）处理。按名字黑名单去拦既不完整又易误伤。

这条存在的意义是**不留静默缺口**：规格明确说出覆盖到哪里，
比让读者以为"所有危险操作都被拦住了"要安全。

### S-CMD-16 布尔修饰符的登记范围必须完整（N15/N16）
`WINDOWS_MCP_ARGUMENTS` 必须是**该工具的完整参数集**，不能自我定义为
"只记录策略会读的键"——那样**漏登记永远查不出**：某个可区分字段没被登记，
测试会认为"布局没用到它"而通过，规则却因此永远命中不了。
`Process` 的 `force` 正是这样漏掉的。

另外"布尔修饰符"的适用范围必须说清：

- `FileSystem` 的 `recursive`/`append`/`overwrite`/`show_hidden` 与 `Process` 的 `force`
  都**登记并读取**（值为上游真值时进入操作文本）；
- 其中当前**只有 `recursive` 与 `force` 被规则使用**，其余登记是为了让
  "值不同则操作文本不同"这一性质可被规则未来使用，而不是"登记了等于拦了"。

测试双向核对：登记为布尔的键必须真在上游是布尔型；上游是布尔型的键不得漏登记。

## 13. 运行时自检（Batch 8）

### S-HOST-06 `winmcp_doctor` 必须能发现上游 schema 漂移
必须提供只读自检工具 `winmcp_doctor`，把"本插件对上游的假设"与
"上游**实际注册**的工具参数"逐项比对，并把差异作为**首要结论**输出。

比对口径：对 `WINDOWS_MCP_ARGUMENTS` 的每个类目，找到注册表里的
`mcp__<serverName>__<类目>`，比较其 `inputSchema.properties` 的键集合。

| 结论 | 含义 |
|---|---|
| 一致 | 报"参数名与登记全等" |
| **上游少了本插件要读的键** | **严重**：规则会静默失效（历史上 `action` vs `mode` 正是这一类） |
| **上游多了未登记的键** | **警告**：可能有可区分字段没被利用（历史上 `Process.force` 正是这一类） |

**为什么必须做成工具而不是只写在文档里**：这类缺陷**只有对着真实注册表才能发现**，
而发现时机决定代价——在点击落空之后发现，比启动自检发现贵得多。
模型也可以在"点击似乎偏了"时主动调用。

此外还必须报告：观测是否存在与年龄、映射是否完整、急停状态、审计可用性与条目数、
命令级策略是否启用及规则条数、持久上下文注入是否开启。

### S-HOST-07 `winmcp_doctor` 必须只读且失败关闭
该工具**不得**改动任何状态。注册表不可读、工具服务缺失或任一检查抛错时，
必须把该项标为"未知/失败"并在总体结论里体现，
**不得**因为查不到就报"全部正常"。

理由：自检工具最常见的危害是给出**虚假的健康结论**——那比没有自检更糟，
因为它会让人停止怀疑。

### S-HOST-08 `winmcp_doctor` 必须复用启动时的配置快照
它不得使用独立配置，以免出现"运行时用 A、自检用 B"的分裂。

### S-CMD-17 `App` 启动解释器必须进入命令级判定
`App` 能带 `executable` + `args` + `cwd` 启动**任意程序**（真机 schema 实测：
`mode`/`name`/`window_loc`/`window_size`/`executable`/`args`/`cwd`）。
因此它是一条**与直接调用 PowerShell 等价的执行路径**，而命令文本规则看不到它。

规则 `app-launch-interpreter`：`mode` 为 `launch` 或 `launch_executable`，
且 `executable`/`name`/`args` 中出现解释器或脚本宿主
（`powershell`/`pwsh`/`cmd`/`wscript`/`cscript`/`mshta`/`rundll32`/`regsvr32`/
`msiexec`/`certutil`/`bitsadmin`/`installutil`/`wmic`）→ **拒绝**。

**诚实声明**（与 S-CMD-04 同一立场）：这是**关键词黑名单，不是安全边界**。
改名、复制解释器、自解压、脚本宿主变体都能绕过；它的价值是把最常见的几种写法
从"静默放行"变成"明确拒绝 + 可读理由"。

**反向要求**：普通应用（`notepad` 等）、`switch`/`resize` 模式必须**放行**——
假阳性会让人整体关掉这个功能，而关掉之后所有规则一起失效。

> 这个缺口是 `winmcp_doctor` 第一次真机运行时发现的：它报出 `App` 少登记 5 个参数，
> 顺着"少登记的字段里有可区分字段"这条线查下去才发现存在未受检的执行路径。
> 这正是把"假设漂移"做成工具的价值。

## 12. 审计可视化（Batch 5）

> **目标**：审计条目是机器可读的 JSONL，但"最近到底做了什么、被拦了什么"
> 需要人一眼看懂。本节把可视化做成**确定性的纯函数 + 两个入口**
> （工具 `winmcp_audit` 与脚本 `scripts/audit-report.mjs`），
> 使同一份日志在任何时候渲染出同样的文本。

### S-VIEW-01 条目必须以原始形状参与统计
可视化只读取条目已有的字段，**不得**按"预期形状"过滤：
字段缺失的条目仍然计入总数（它们代表真实发生过的事）。
- 缺失 `decision` → 归类为 `unknown`；
- 缺失 `tool` → 归类为 `(unknown)`；
- 非对象条目在进入可视化之前就已被 `read()` 滤掉（S-AUDIT-05），此处不重复处理。

### S-VIEW-02 统计口径固定
摘要必须**至少**给出以下口径（全部基于同一份输入，互不矛盾）：

| 口径 | 定义 |
|---|---|
| `total` | 条目总数 |
| `byDecision` | 按 `decision` 计数（含 `unknown`） |
| `byAction` | 按 `action` 计数（含 `unknown`） |
| `byTool` | 按 `tool` 计数（含 `(unknown)`），降序、同频按名称升序 |
| `allowed` / `denied` | `allowed === true` 的条数 / `allowed === false` 的条数 |
| `byCode` | 被拒条目的 `code` 计数，降序 |
| `unknownOutcome` | `allowed` 既非 `true` 也非 `false` 的条数 |
| `malformed` | 非对象条目的条数（诊断用） |

**允许额外提供诊断字段**（当前有 `unknownOutcome` 与 `malformed`），
但额外字段**不得**与上表任何口径矛盾，也不得改变它们的含义。
原措辞"只给出"过严：诊断字段对排障有用，禁掉它们只会逼实现把它们藏起来（对抗性验证 V14）。

`byDecision` 的合计必须等于 `total`；`byTool` 的合计同理。
**"合计等于总数"是本节唯一的不变式**，由测试强制。

**字段名以本表为准**（对抗性验证指出过一次 `denyCodes`/`byCode` 不一致）：
规格与代码必须用同一个名字，由测试断言字段存在性。

### S-VIEW-03 渲染必须人类可读且稳定
渲染结果必须满足：
- 首行是标题，包含条目数；
- 分区顺序固定（概览 → 分类 → 最近条目）；
- 最近条目按时间**倒序**（最新在前）；时间不可用的条目排在最后而不是丢弃；
- **等时间戳保持输入顺序**（稳定排序，裁决 N6）。禁止依赖"输入反转输出也反转"——
  那等于没排序。可判定断言：同 `at` 的一组条目，正序输入得到正序输出。
- 每条一行，包含：时间（HH:MM:SS 或 `--:--:--`）、判定、工具、代码、原因摘要；
- 原因超长时截断并标注省略号；
- **空输入**输出明确的"暂无记录"，而不是空白或报错。

### S-VIEW-04 展示不得抛出
输入为 `undefined`/非数组/含畸形条目时，渲染与统计都必须返回可用结果，
**不得**抛异常（它是一个诊断功能，不能成为新的故障点）。

### S-VIEW-05 时间显示容错
`at` 不可解析时不显示伪造时间：用 `--:--:--` 占位，并把该条排在末尾，
同时保证它仍计入统计（S-VIEW-01）。

### S-VIEW-06 两个入口必须共享同一实现
工具 `winmcp_audit` 与脚本 `scripts/audit-report.mjs` 必须调用同一批纯函数，
不得各自实现一遍渲染（防止"工具里看到一套、脚本里看到另一套"）。
**两个入口的默认条数必须相等**（当前都是 `DEFAULT_RECENT = 10`），
否则"同一份日志渲染出同样的文本"这句导语不成立（对抗性验证 V13）。
工具侧新增 `view` 参数：`raw`（默认，原始 JSON）与 `summary`（可视化）。

### S-VIEW-07 工具名必须在展示前归一化
审计里同一个工具会出现两种写法：闸门写的是**去前缀**名（`PowerShell`），
而策略层写的是**带前缀**名（`mcp__winmcp__PowerShell`）。
可视化必须把它们归一到**同一个键**，否则"按工具"分区会把一次调用拆成两行，
总数看起来翻倍。

归一化规则：去除**大小写不敏感的** `mcp__<server>__` 前缀后 `trim()`；
结果为空串时按 `(unknown)` 处理（与 S-VIEW-01 的"缺失 tool"一致，裁决 N7）。
**只影响展示**：审计文件里存的仍是原始值，不得为了好看去改写日志。

## 8. 桥接边界（MCP 结果 → 观测 → 闸门）

本章描述「一次 Windows-MCP 调用从 MCP 形状的结果变成一条观测，再变成一次放行/拒绝」
这条链路上的对外承诺。

**为什么必须独立成域**：第 1–7 章的承诺都假定「结果已经到达插件」，但真实故障多数
发生在更早的一步——桥没有把结果投影出来、结果形状不对、上游报错、图片进不来。
这些边界的处理方式直接决定模型看到什么、闸门依据什么，因此必须和坐标/闸门同级地
写成可判定的规格，而不是留在实现细节里。

**可复现性边界（本批新增）**：本章的条目全部可用 `test/harness/fake-mcp.js`
（可编程假 MCP 服务器，按真实抓取形状产生字节级文本）在**无桌面依赖**下重放；
「真机仍有差异」的部分由第 9 章显式记录。假服务器**不**证明上游行为，只证明
「给定的上游形状下，本插件的行为符合承诺」。

### S-BRIDGE-01 上游内容只追加不丢失
一次观测工具的结果经 `tools/post-execute` 处理后，返回的内容块必须以上游原始块
**原样开头**（逐字节保留文本，含中文、em dash、CRLF 与 `\r` 残留），本插件追加的
映射块只能出现在其后。

### S-BRIDGE-02 可交互元素与窗口事实必须解析出来
结果里给出 `Focused Window` 表格、`Opened Windows` 表格与带坐标的 UI 树行时，
观测必须解析出焦点窗口的名称与句柄、全部已打开窗口、以及全部带坐标的可交互元素。

### S-BRIDGE-03 畸形响应不得抛出，也不得被当成观测
`value` / `content` 缺失、类型错误、文本不是字符串等畸形结果经 `tools/post-execute`
时必须**不抛出**、保持原决定，且**不得**记录成一条观测（不得凭空造出观测）。

### S-BRIDGE-04 上游报错如实入库且不产生观测
`isError === true` 的结果必须记录一条 `decision = error` 的审计条目（带原因），
**不**产生观测，且结果保持原样不被改写。

### S-BRIDGE-05 图片无法被桥接纳时不得谎报
图片块因媒体类型不被接纳（不在允许列表）时：桥**完整保留**元数据文本与原始 `value`，
只是内容块里没有图片；观测的 `image.hasImage` 必须为 `false`。不得把「确认不了」
写成「确认有图」，也不得把整次观测丢弃。

### S-BRIDGE-06 UI 树的两种合法形状
`@U-05`。UI 树区段只有两种合法形状：

1. **完整树**：含带坐标的行，必须解析出这些元素；
2. **占位空树**（如 `UI Tree:` 后紧跟 `No elements`）：可交互元素数必须为 `0`。

占位文本**绝不**能被解析成一个可交互元素（那等于凭空造出一个元素）。
两种形状下，只要 `Cursor Position` / `Screenshot Region` / `Screenshot Coordinate Scale`
仍在，观测就必须照常成立且映射可用——不得因为树缺失而丢掉整条观测。

### S-BRIDGE-07 并发写入的一致性与隔离
`@U-06`。多个 agent 的观测/动作交错，或同一 agent 多次 `post-execute` 同时在途时：

1. 各会话桶的观测互不污染（延续 S-OBS-03 / S-GATE-10）；
2. 观测 id 在进程内仍然全局唯一、无重复；
3. 审计文件每一行都是独立的合法 JSON 对象——**不得**出现交错的半截行。

### S-BRIDGE-08 传输失败不得产生半条观测
服务器不响应、或响应中途断开时，插件**不得**：
产生观测、递增观测代次、写入「动作已完成」类审计条目，或把它当成一次成功动作。
后续一次完整响应必须从干净的观测序号继续（不得留下半条观测造成的空洞或错位）。
可复现的故障注入由 `test/harness/fake-mcp.js` 的 `neverSpeak` / `disconnectAfterChunks`
提供（见 SYS_SPEC 第 9 章：真机 bridge 的实际超时行为不由此证明）。

## 9. 尚未验证的事项（必须显式声明）

### 9.0 上游能力边界（实机测得，必须先声明）

**运行中的 Windows-MCP 与本仓 `_recon_windows_mcp/` 检出不是同一个版本。**
2026-10-11 实机测得 live 服务端能力如下，写规格与写规则时必须以它为准：

| 项 | 实测结果 |
|---|---|
| 工具数 | **20**：App, Click, Clipboard, DisplayInventory, FileSystem, Move, MultiEdit, MultiSelect, Notification, PowerShell, Process, Registry, Scrape, Screenshot, Scroll, Shortcut, Snapshot, Type, Wait, WaitFor |
| `ControlStatus` | **不存在**（0.8.8 新增的第 21 个工具；`--dump` 与工具表均无） |
| `Screenshot` / `Snapshot` 的 `region` 参数 | **不存在**：`Screenshot(region=[400,300,1200,800])` → `Unexpected keyword argument`（0.8.8 才加） |
| `display` 参数 | 存在且**有校验**：`Screenshot(display=[0,1])` → `Invalid display index 1. Available displays: 0`（错误文本干净可读） |
| 截图上限 | 上游把截图封顶到 1920x1080（本机 2560x1440 → 1920x1080，`coord_scale = 1.333333 = 2560/1920` 与之吻合） |

**为什么要专门写这一节**：`_recon_windows_mcp/`（0.8.8）与 PyPI 稳定版（0.8.5）的能力集**不同**。
照检出写规格会得到"规格说能用的参数在真机上不存在"，
或者"规格没覆盖的真机上其实有"——两者都会造成错误结论。
引用上游行为时必须注明**依据的是哪一份**。

### 9.1 坐标换算的真机复核（2026-10-11，两点法）

**唯一可靠的坐标探针是「光标往返」**：用 `Move` 把光标放到已知屏幕坐标，
再由服务端回报 `Cursor Position`。服务端回报的是它**自己**的位置真值，
因此这条路径不依赖任何图像解读或人工目测。

| 我要求移动到 | 服务端回报 |
|---|---|
| (200, 100) | `Cursor Position: (200, 100)` |
| (2000, 1200) | `Cursor Position: (2000, 1200)` |

两点都精确吻合，说明"屏幕坐标 → 上游元数据"这一环无系统性偏移。
同时 `coord_scale = 1.333333` 与 `2560/1920` 完全一致，
**证实上游 Snapshot 自己文档里那句"multiply image coordinates by the ratio of
original size to displayed size"就是 `coord_scale`**——两处描述的是同一个换算。

> 注：这与"不要乘附件宽/上游图片宽"并不矛盾。被证伪的是**在 `coord_scale`
> 之外再乘一次**（双重缩放，会把坐标算偏 ~33%）；而 `coord_scale` 本身**就是**那个比例。

#### 关于 `use_annotation=true` 的更正（重要）

它**不是**光标十字准星探针。读上游 `desktop/service.py:1425-1456` 可知它做的是：

```python
draw.rectangle(clipped_box, outline=color, width=2)   # 每个 UI 元素的编号方框
draw_label(str(label_index), ...)                      # 方框角上的序号
```

即"给每个可交互元素画一个带序号的彩色矩形"，用于让模型把图像里的方框与
UI 树里的元素**对应起来**。因此：

- 它能做的是**元素级**核对（"第 3 号方框对应 UI 树第 3 个元素"）；
- 它**不能**给出坐标级残差——方框位置来自元素的 `bounding_box`，
  与换算公式并非独立来源，用来自证会循环论证；
- `width_reference_line`/`height_reference_line` 的网格**需要 `use_vision=true`**
  （上游 `tools/_snapshot_helpers.py:78` 要求两者同时给出，且描述写明需开 vision）。

先前把 `use_annotation` 记为"无残差坐标探针"是**错的**，此处更正。
