> **这份文件是什么**：对抗性验证者按 `SYS_SPEC.md` 构造反例时，报回 16 条
> 「**按现状不可判定**」的规格缺陷——不是实现错了，而是**规格本身写得无法判定**。
> 本文件逐条记录裁决：采用哪种解释、为什么、以及它属于哪一类处置。
>
> **为什么必须单独记录**：不可判定的规格会让后续每个批次都建立在含糊的承诺上。
> 而"改规格"这件事如果只发生在对话里，下一个验证者还会踩同一个坑。
>
> **编号规则**：`A-<序号>`，与需求编号 `S-<域>-<序号>` 分开——它们是**对规格的裁决**，
> 不是新的行为需求。因此不参与 `spec/COVERAGE.md` 的覆盖门（门禁只统计 S-* 条目）。
>
> 处置分类：
> - **CODE** —— 裁决要求改代码（已改，并有测试）
> - **WORD** —— 只改规格措辞，让原本对的行为变得可判定

## 一、已裁决（CODE：改了代码 + 加了测试）

### A-01 `coord_scale` 行存在但值非法 → 诊断必须区分「缺行」与「值非法」
- 关联：S-MAP-02、S-MAP-05
- 裁决：行存在但不是有限正数（`0` / `-1` / 非数字）时，换算退化为 `1.0`（**不**让映射变得不可用），
  但诊断必须写明「行存在但值非法」，不得说「缺少该行」。
- 理由：区分这两种情况决定排障方向。说错会让人去查上游为什么没输出，而实际上上游输出了、值是坏的。
- 落地：`parseCoordScaleDetailed()` 返回 `{present, value, invalid}`；观测新增
  `rawCoordScaleInvalid` 字段；诊断按它分叉。

### A-02 `Original Size` 出现非正值 → 视为缺失
- 关联：S-MAP-05
- 裁决：任一维 `<= 0` 视为**缺失**（`originalSize = null`）并给出诊断。
- 理由：`(0,0)` 的语义是"上游给不出尺寸"，不是"尺寸为零的图片"。当有效值会让后续所有
  按尺寸做的推导静默算错（分母为零）。
- 落地：`parseOriginalSizeDetailed()`；观测新增 `rawOriginalSizeInvalid`。

### A-03 `Screenshot Region` 行存在但不可解析 → 视为缺失 + 区分性诊断
- 关联：S-MAP-05
- 裁决：不可解析时 `region = null`（原点按 `(0,0)` 退化），诊断必须说明"行存在但无法解析"。
- 落地：`parseRegionDetailed()`；观测新增 `rawRegionInvalid`。

### A-04 S-MAP-06 的吸附会放大误差 → 吸附必须与缩放相关
- 关联：S-MAP-06
- 裁决：**只在 `screenPerImagePx >= 1` 时吸附**到整数；否则不吸附、保留 6 位。
  正向（屏幕）在 `>= 1` 时保留 3 位小数，反向（图片）保留 3 位。
- 理由：实测 `coord_scale = 0.0001` 时，固定"与整数相差 < 0.002 就吸附"会把往返误差
  放大到 **19.9 图像像素**，与"远小于 1 像素"的说法直接矛盾。
- 落地：`roundFriendly(n, scale)` 按 scale 分叉；误差界断言 `|Δpx| <= 0.002 / screenPerImagePx`。

### A-05 `read()` 必须只返回对象记录，且统计跳过行数
- 关联：S-AUDIT-05
- 裁决：`read()` 只返回 JSON **对象**；`5` / `"x"` / `null` / `[]` / `true` 这类
  "合法 JSON 但不是记录"的行按损坏行处理，计入 `stats().skipped`。
- 理由：消费方读 `entries[i].observationId` 会直接炸。而"静默丢弃"与"统计到丢了多少行"
  在排障时完全不同。
- 落地：`parseLines()` 返回 `{entries, skipped}`；`stats()` 增加 `skipped`。

### A-06 急停的两个计数必须分开
- 关联：S-SAFE-01
- 裁决：`engageCount` = **累计 engage 调用次数**（含重复）；`engageSeq` = **成功启用序号**
  （重复不递增）。`engagedAt` / `reason` 取首次成功启用的现场；`release()` 后再 `engage()`
  是新的一次（序号 +1、刷新时间与原因、`releasedAt` 重置为 `null`）。
- 理由：规格原文自相矛盾（同段既说"不增加启用计数"又说"记录累计尝试次数"），
  一个字段无法同时承担两种语义。
- 落地：拆字段；`features/safety-switch.feature` 与相关测试同步。

### A-07 配置值被强转或回退默认时必须留下警告
- 关联：S-HOST-04
- 裁决：任何配置字段被强转或回退默认时，必须 `warn` 一条含
  **键名 / 收到值 / 采用值**的日志。
- 理由：静默把 `maxObservationAgeMs: 'x'` 变成 `60000` 是"看起来生效其实没生效"的典型缺陷，
  用户永远查不到原因。
- 落地：`normalizeConfig(raw, env, onCoerce)` 新增回调；`apply()` 接到 logger。

### A-08 不可解析的 `at` 必须用写入时刻兜底并打标记
- 关联：S-AUDIT-03
- 裁决：`at` 不可解析（`Date.parse` 为 NaN）时用**写入时刻**的 ISO 字符串，
  并在条目上标 `atCoerced: true`。不得原样保留原字符串（那会破坏按时间排序）。
- 落地：`coerceTime()` + `normaliseEntry()` 的兜底分支。

## 二、已裁决（WORD：只改规格措辞）

### A-09 S-GATE-07「任何情况下」过宽
- 裁决：改为——只读观测工具**不因以下原因**被拦：观测缺失、观测过期、代次落后、
  映射不完整、急停启用。**操作者显式配置的策略判定不在此列**（例如 `denyTools` 明确拒绝它）。
- 理由：原措辞与"策略可以拒绝任何工具"直接冲突，无法同时满足。

### A-10 S-GATE-02 的配置逃生口必须写进规格
- 裁决：显式承认三个开关——`requireObservation=false` 关闭 S-GATE-02、
  `requireCoordinateMapping=false` 关闭 S-GATE-09 的提示、`requireProcessMatch=false`
  关闭 S-GATE-05。**除这三个显式开关外，任何配置不得使 S-GATE-* 失效**（S-CFG-02）。

### A-11 S-SAFE-04 的审批边界
- 裁决：授权在 `now - grantedAt > approvalTtlMs` 时失效；**恰好等于上限时仍然有效**
  （与 S-GATE-03 的边界约定一致）。`approvalTtlMs <= 0` 表示立即失效。

### A-12 S-HOST-02 必须定义「上游内容源」
- 裁决：上游内容源依次取 `result.content`（数组）→ `result.value.content`（数组）→
  `result.value`（字符串）。富化结果**必须以上游内容开头**，追加块只能位于其后。
  上游为空时，追加块本身就是结果。

### A-13 S-CFG-01 必须定义「yml 中缺失的键」
- 裁决：以**键集合与 `DEFAULTS` 全等**为一致；某键在 yml 中缺失即不一致。
  例外：取值由环境在运行期决定的**派生键**（当前只有 `auditFile`）不要求在 yml 中出现，
  但必须在 README 中标注为「派生」。

## 五、本裁决的元教训

1. **"不可判定"和"错误"是两种缺陷。** 前者更危险——它让所有基于它的测试都变成
   "看起来在验证，其实没有"。因此本文件的分量不低于 `SYS_SPEC.md`。
2. **验证者必须能指出规格的问题，而不只是实现的问题。** 16 条里有 13 条最终落在
   规格措辞上，只有 A-01…A-08 需要改代码。
3. **边界值必须写进规格。** A-11（恰好等于 TTL）与 S-GATE-03（恰好等于上限）是同一种
   错误的两处；不写清楚就一定会有一个实现方按另一种解释写。

### V1 —— 卷根的命名空间写法整条绕过（失败开放）

| 写法 | 规范化后 | 修复前 |
|---|---|---|
| `C:\` / `C:` / `C:/` | `c:/` | 拦 ✅ |
| `\\?\C:\` | `/?/c:/` | **放行 ❌** |
| `\\.\C:\` | `/./c:/` | **放行 ❌** |

`\\?\` 与 `\\.\` 表示**同一个路径**，只是要求不做路径规范化；上游
`Path('\\\\?\\C:\\').is_dir()` 为真 → 会走 `shutil.rmtree`，**真的清空分区**。

**处置**：并入 `S-CMD-02` 的规范化步骤 4（在词首或空格之后去掉这两个前缀），
新增 `S-CMD-15` 说明"等价写法必须穷尽"，并加回归测试。

### V2 —— 我自己的修复制造了假阳性（规格错误在先）

上一轮我凭"上游会宽松处理"**推断**出真值语义，并写进规格要求
"必须覆盖 `'1'`、`'yes'`、非零有限数"。上游真源码是：

```python
recursive = recursive is True or (isinstance(recursive, str) and recursive.lower() == 'true')
```

即**只有**布尔 `True` 或 `lower()` 后等于 `'true'`；**不 trim**。
所以 `'1'`/`'yes'`/`1`/`' true '` 上游都判**假**，不会递归删除；
实现照规格放宽后把它们当成真，于是 `recursive:'yes'` 被拒——
**正是本模块自己声明最怕的假阳性**。

**处置**：`isTruthyFlag` 改为逐字照抄上游；`S-CMD-12` 更正，并写下总则：
**凡是"上游语义"，必须读源码，不得推断；安全方向不等于"宁可多认"。**

> 附带发现：我原来的测试用 `C:\tmp\a.txt`（普通目录）断言假值放行，
> 而普通目录本来就不命中卷根规则——**该断言毫无鉴别力**。
> 变异测试把它暴露出来（`truthy-dialect-loosened` 存活），改用**卷根**测后变异体即被杀。

### V3 —— `Process` 的 `force` 被漏登记，强杀规则不可达

上游 `tools/process.py` 有 `force: bool | str = False`，决定
`p.kill()`（无条件强杀）还是 `p.terminate()`。但 `WINDOWS_MCP_ARGUMENTS.Process`

### N17 —— 变异工装的最坏失败模式（实测，不是理论）

验证者用 `taskkill /T /F` 实测：**第 1 次试验就命中**。强杀后
`lib/commands.js` 里留下 `if (exempt.has(rule.id))` → `if (false)`——
一处**语法正确**的安全缺陷（`allowRules` 豁免永久失效），
stdout 只到"杀死 2/26"，**没有任何失败信号**，`git status` 只显示一行 ` M`，
一次 `git commit -a` 就会入库。触发条件（取消长命令 / CI 超时 / 关终端 / 重启）日常很常见。

**处置**：`mutants.mjs` 改为在**影子副本**里跑——真实工作树在整个运行期间
**一个文件都不碰**，强行终止最多留下一个临时目录。另外：

- 记录运行前后的 `git status --porcelain`，只在**发生变化**时报警
  （直接断言"必须为空"会误报开发者自己的未提交改动——第一次实现就踩了）；
- 变异后先 `node --check`，语法错误的变异体单独报为"变异体写坏了"，
  **不计入杀死数**（连解析都过不了的变异体没有验证任何东西）；
- 收尾删除影子副本。

**总则**：`finally` 挡不住强杀。唯一可靠的边界是"根本不在真实工作树里改文件"。

### 第三轮的元教训

6. **"读源码"与"推断语义"必须分清。** V2 是这条的总代价：我推断上游"宽松"，
   于是修复方向反了，把安全特性变成了假阳性。凡引用上游行为，
   必须给出源码位置；给不出就只能标为假设并加诊断，不能写进规格当要求。
7. **自我定义的口径会让遗漏隐形。** `WINDOWS_MCP_ARGUMENTS` 自称"只记录策略会读的键"，
   于是漏登记永远查不出（N15）。口径必须是**外部标准**（真实 schema），并与代码**全等**比对。
8. **测试必须有鉴别力。** 用普通目录去测"卷根规则不该命中"是空断言；
   变异测试是发现这类空断言的有效手段（它比覆盖率诚实得多）。
